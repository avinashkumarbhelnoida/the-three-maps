# THE THREE MAPS — 201.80A ARCHITECTURE AUDIT

## Status
AUDIT COMPLETE — HARDENING REQUIRED BEFORE PRODUCTION RELEASE

Baseline: 201.79Q / 110 passing tests.

## Executive conclusion
The implementation follows the frozen layered architecture and the core decision engines are separated. The audit found no evidence that the major frozen state-machine boundaries have been intentionally collapsed. However, four material implementation gaps must be resolved before a release candidate: complete ontology data, first-class system identity in axis aggregation, calculation-version lineage correctness for signals, and explicit numerology Y-vowel policy. These are hardening items, not reasons to discard the architecture.

## Findings

### A-001 — COMPLETE THE AUTHORITATIVE 20 THEME / 200 SUB-THEME CATALOGUE
Severity: P1
Status: OPEN

The registry intentionally contains the 28 axes and 56 poles but does not yet contain the authoritative 20 Themes / 200 Sub-Themes. This was correctly left un-invented. The product cannot claim full ontology coverage until the canonical catalogue and mappings are loaded.

Required action:
- Load the authoritative Theme/Sub-Theme catalogue.
- Version it under OV.
- Add mapping and applicability records.
- Add completeness tests: 20 themes, 200 sub-themes, parent-child integrity, axis/pole references.

### A-002 — AXIS AGGREGATION NEEDS FIRST-CLASS SYSTEM IDENTITY
Severity: P1
Status: OPEN

The current axis aggregation derives system identity by splitting `signal_id` on `:`. Signal IDs are hashed identifiers and therefore are not a reliable system boundary. The domain model already has source-system identity on Signal, but PoleEvaluation currently retains only signal IDs.

Required action:
- Add authoritative source-system identity to PoleEvaluation or a dedicated contributor object.
- Aggregate by that field only.
- Preserve per-system pole results in `AxisResult.system_results`.
- Add tests for three systems, duplicate signals, and equal-weight aggregation.

### A-003 — SIGNAL CALCULATION VERSION LINEAGE BUG
Severity: P1
Status: OPEN

`generate_signal()` currently assigns `mapping.ontology_version` to `Signal.calculation_version`. Ontology version and calculation version are separate governance domains and must never be substituted.

Required action:
- Require an explicit calculation version in signal generation or inherit it from authoritative upstream evidence/calculation lineage.
- Test version-domain separation.

### A-004 — NUMEROLOGY Y-VOWEL POLICY MUST BE VERSIONED
Severity: P2
Status: OPEN

The current implementation treats Y as a consonant because the vowel set is hard-coded to AEIOU. The methodology architecture states that Y treatment should be methodology-configured.

Required action:
- Add explicit Y policy to methodology configuration.
- Preserve it in the methodology version.
- Add boundary tests for names containing Y.

### A-005 — AXIS COVERAGE IS CURRENTLY PROVISIONAL
Severity: P2
Status: OPEN

Axis coverage currently behaves as a presence flag rather than the canonical expected-relevant-weight coverage concept. This should not be confused with System Score coverage.

Required action:
- Define axis-level expected evidence semantics.
- Compute coverage from expected relevant axis evidence where applicable.
- Keep Axis Status separate from System Score Status.

### A-006 — ASTROLOGY YOGA ENGINE REMAINS UNIMPLEMENTED
Severity: P2
Status: OPEN

The calculation engine intentionally does not implement yoga interpretation as simplistic boolean conditions. This is methodologically correct. A production astrology engine nevertheless requires a versioned yoga formation/strength/context/activation module before yoga-derived signals can be authoritative.

Required action:
- Define yoga registry and formation rules.
- Separate formation, strength, context, and activation.
- Add regression tests before mapping yoga signals.

## Confirmed architectural strengths

- Engine separation is preserved.
- Deterministic calculations are separated from generative explanation.
- Missing evidence is not automatically converted to negative evidence.
- UNAVAILABLE is not zero-filled.
- PARTIAL remains score-bearing without automatic coverage penalty.
- S6 and S7 are distinct.
- Dual-pole support is not itself contradiction.
- Contradiction requires validated opposing evidence.
- Thresholds are centralized.
- Version and lineage objects exist.
- API remains a boundary/orchestration layer.
- Frontend does not own business rules.
- Tests cover the major frozen state transitions.

## Release gate recommendation

Do not declare production-ready until A-001 through A-003 are closed. A-004 through A-006 should be closed before claiming full methodological coverage. After closure, rerun the complete Master Test Suite and the 201.79Q regression suite.
